网络安全

基于 HMAC-SHA256 的 API 认证系统实现：签名、防重放与时序攻击防御

May 22, 2026
阅读时长: 7 分钟

前言

这是网安课程的期末大作业：基于HMAC的 API身份认证系统。该系统的运行逻辑是让客户端每次发请求时附上一个用密钥算出来的签名，服务端收到后重新进行计算并对比，再判断是否通过。这个认证机制用得非常广泛，阿里云、微信支付等接口签名都是用的这套机制。

项目概述

为什么做这个

传统的API认证方案（比如只传一个 token）有两个弱点：一是 token 被截获就能直接用，二是请求内容可以被中间人悄悄改掉而服务端无法察觉。

HMAC可以同时解决这两个问题——它把请求内容本身也纳入签名计算，任何字段被篡改，签名将立即失效。再配合时间戳和Nonce，就能将重放攻击也一同解决。

核心功能

  • 客户端签名：用共享密钥对请求内容计算HMAC-SHA256，附在请求头里发送
  • 五层服务端校验：请求头完整性 → API Key合法性 → 时间戳有效性 → Nonce唯一性 → 签名正确性
  • 防重放攻击：Timestamp窗口+Nonce
  • 防时序攻击：用 hmac.compare_digest() 替代 == 做固定时间字符串比较
  • 六个自动化测试用例：覆盖正常请求、数据篡改、过期请求、重放攻击、非法Key、缺少请求头

背景知识概念

HMAC 和普通哈希有什么区别

普通哈希（比如 SHA256）只对内容计算摘要，任何人都能算：

1

SHA256("hello") → 结果是固定的，安全性较低

HMAC 在计算时引入了一个只有双方才知道的密钥：

1

HMAC(SecretKey, "hello") → 没有密钥就无法得出明文

SHA256 能验内容没被改，但不能证明是谁发的；HMAC方案既能验内容没被改，又能证明是谁发的。

数学公式

$$HMAC(K, m) = H\bigl((K \oplus opad) \parallel H((K \oplus ipad) \parallel m)\bigr)$$

其中 $H$ 是哈希函数（这里用 SHA256），$K$ 是密钥，$m$ 是消息，$opad$ 和 $ipad$ 是固定的填充常量。

什么是重放攻击

攻击者不需要破解密钥，只需要把你的合法请求原封不动地再发一遍：

1
2

正常流程：客户端发出「发起转账」的签名请求 → 服务端执行
重放攻击：攻击者截获这个请求，再发一遍 → 如果服务端不防，再转一次

防御方案是 Timestamp + Nonce：时间戳可以限制请求的有效期，Nonce可以保证同一个请求只会被服务端处理一次。

什么是时序攻击

字符串比较 if A == B 是短路的——发现第一个不同字符就立刻返回。

攻击者可以通过测量服务端响应时间的微小差异，推断出签名在哪一位开始不同，从而逐字节推测出正确签名。

防御方式是用固定时间的比较函数，无论在哪一位出现差异，耗时都完全一样：

1
2
3
4
5

# 危险写法
if server_sig == client_sig:  # 短路比较，有时序漏洞

# 正确写法
hmac.compare_digest(server_sig, client_sig)  # 固定时间，无漏洞

import hmac
import hashlib

def generate_signature(secret_key, method, path, timestamp, nonce, body):
    # 把请求的所有关键字段拼成一个字符串
    # 任何字段被改动，签名就会完全不同
    signing_string = f"{method.upper()}\n{path}\n{timestamp}\n{nonce}\n{body}"

    mac = hmac.new(
        key=secret_key.encode("utf-8"),
        msg=signing_string.encode("utf-8"),
        digestmod=hashlib.sha256,
    )
    return mac.hexdigest()

def verify_signature(expected_sig, client_sig):
    # 固定时间比较，防时序攻击
    return hmac.compare_digest(expected_sig, client_sig)

签名字符串的格式是：

1

POST\n/api/v1/resource\n1748000000.123\nabc123def456\n{"item":"macbook","amount":1}

用 \n 分隔每个字段，保证字段之间有明确边界，不会发生拼接歧义（例如 path 末尾正好有数字和 timestamp 开头粘在一起）。

2. Nonce 存储：app/database.py

一开始我们的方案是用 set() 存 Nonce，但是这个方案有两个致命问题。

问题一：内存无限增长

Nonce只进不出，服务跑久了会导致内存爆满。于是我们把 set 改成 dict，每条Nonce会记录自己的过期时间，后台将定期清理过期的Nonce：

NONCE_TTL = 300  # Nonce 有效期与时间戳窗口一致
_nonce_store: dict[str, float] = {}  # {nonce: expire_timestamp}
_store_lock = threading.Lock()

def _cleanup_expired_nonces():
    while True:
        time.sleep(60)
        now = time.time()
        with _store_lock:
            expired = [k for k, exp in _nonce_store.items() if exp <= now]
            for k in expired:
                del _nonce_store[k]

# 后台线程，daemon=True 保证主进程退出时自动销毁
_cleanup_thread = threading.Thread(target=_cleanup_expired_nonces, daemon=True)
_cleanup_thread.start()

问题二：服务重启后 Nonce 记录丢失

内存存储在服务重启后会清空，已消耗的 Nonce 相当于失效，之前截获的请求又可以重放了。is_nonce_used() 里加了过期判断：

def is_nonce_used(nonce):
    now = time.time()
    with _store_lock:
        exp = _nonce_store.get(nonce)
        if exp is None:
            return False       # 从未使用过
        if exp <= now:
            del _nonce_store[nonce]
            return False       # 已过期，视为未使用
        return True            # 有效期内且已使用 → 重放攻击

async def verify_hmac_dependency(request: Request) -> str:

    # 第一层：请求头完整性
    api_key          = request.headers.get("X-API-Key")
    timestamp_str    = request.headers.get("X-Timestamp")
    nonce            = request.headers.get("X-Nonce")
    client_signature = request.headers.get("X-Signature")
    if not all([api_key, timestamp_str, nonce, client_signature]):
        raise HTTPException(401, "缺少必要的安全请求头")

    # 第二层：API Key 合法性
    if not is_valid_client(api_key):
        raise HTTPException(401, "无效的 API Key")

    # 第三层：时间戳有效性
    client_time = float(timestamp_str)
    if not (TIMESTAMP_MIN <= client_time <= TIMESTAMP_MAX):  # 防溢出
        raise HTTPException(400, "时间戳超出有效范围")
    if abs(time.time() - client_time) > TIMESTAMP_THRESHOLD:
        raise HTTPException(401, "请求过期（时间偏差超过 300 秒）")

    # 第四层：Nonce 唯一性
    if is_nonce_used(nonce):
        raise HTTPException(401, "Nonce 已被使用，拒绝重复请求")

    # 第五层：HMAC 签名验证
    body_str = (await request.body()).decode("utf-8")
    expected = generate_signature(get_secret_key(api_key),
                                  request.method, request.url.path,
                                  timestamp_str, nonce, body_str)
    if not verify_signature(expected, client_signature):
        raise HTTPException(401, "签名不匹配，数据可能被篡改")

    add_nonce(nonce)  # 验证通过后记录 Nonce
    return api_key

校验顺序是按占用资源从低到高排列的：查请求头和数据库几乎不占用任何资源，而HMAC计算占用最大，放最后。这种方式可以防止攻击者消耗服务器的计算资源。

踩坑记录

坑一：只有时间戳没有 Nonce，5 分钟内可以无限重放

问题描述： 最开始的方案只加了时间戳校验，认为5分钟窗口足够安全。但思考过后发现实际上：

1
2

攻击者在第 1 分钟截获了合法请求
在第 4 分钟重新发出去 → 时间戳仍在窗口内，服务端无法区分

5分钟内的任何截获请求都可以重放，在大型项目中是一个非常严重的问题。

解决方案： 加入Nonce。每个请求生成一个随机字符串，服务端处理完就记录下来，发现相同 Nonce的请求一律拒绝。

坑二：Nonce 集合只增不减，内存会撑爆

问题描述： USED_NONCES = set() 这个集合从来不删除，只会一直增加。当服务运行一段时间后内存会持续增长，跑得足够久就会导致内存溢出然后整个系统崩溃。

Nonce 只需要在时间戳有效窗口内保证是唯一的，300秒前的旧Nonce再怎么进行重放攻击也会被时间戳校验拦截，没必要永久保留。

解决方案： 把 set 改成带过期时间的 dict，配合后台清理线程，让 Nonce 自动在 300 秒后被清除，内存始终维持在合理水位。

项目总结与展望

总结

做得还行的地方： 五层校验形成了完整的纵深防御，每一层针对不同的攻击向量，缺任何一层都有漏洞。密码学实现严格使用 Python 标准库，没有引入不可控的第三方依赖。hmac.compare_digest() 这个防时序攻击代码在很多大企业项目中也被使用。

不足之处： Nonce 存在内存里，服务重启后历史记录丢失；API Key 和 Secret Key 硬编码在代码里，实际应该存数据库并支持禁用和轮转。
