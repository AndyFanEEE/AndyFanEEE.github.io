从零实现一个可信旅行规划 Agent：FastAPI + LangGraph + RAG + 动态证据验证 + 地区感知社交信号

Jul 14, 2026
阅读时长: 18 分钟

前言

在学习的过程中想着做一个ai项目，但是一直没什么灵感。最近刚好有什么福建南平的研习活动，我也想着找一天去其他省份旅游一下，目前也有很多旅游规划ai应用，不过这些ai经常给出的信息不符合实际，而且可能会混杂一些营销号的虚假广告信息，还需要自己去核实。于是我决定自己利用vibe coding做一个ai旅游规划助手，边学边写。目前先做第一版，之后再慢慢完善

1. 项目背景：为什么要做可信旅行规划助手

普通 AI 旅行规划最大的问题，不是行程规划的不好，而是计划里会混杂很多不实信息。

比如你让大模型规划东京三日游，它可能会给你一份看起来很完整的路线：上午去哪，下午去哪，晚上吃什么，地铁怎么坐，景点几点关门，甚至还会补一句“建议提前预约”。问题是，这些信息里可能混着：

  • 不存在或已经关闭的景点；
  • 过期的营业时间；
  • 编造的票价和预约规则；
  • 不适合当天交通或天气的安排；
  • 来自博客、广告页、SEO 内容农场的低质量信息；
  • 社交平台上未经核验的传言。

旅行规划跟普通聊天不一样。它直接影响用户的时间、预算、路线和现实体验。一个“听起来合理”的错误建议，可能让用户白跑一趟。

所以 TrustTrip 的目标不是生成一份漂亮的行程，而是生成一份可验证、可解释、可信度可追踪的旅行计划。

我把它的定位概括成一句话：

1

TrustTrip = 旅行规划 Agent + 可信证据验证 + 动态信息核验 + 地区感知信息发现

它不是单纯和大模型说“帮我安排一下这个计划”，而是把旅行规划拆成多个阶段：

  1. 先生成行程草案；
  2. 再找候选 POI；
  3. 再为每个推荐找证据；
  4. 再做 Review；
  5. 最后才生成用户能看到的计划。

在这个过程中，Evidence 不是装饰品，而是整个系统的核心数据结构。每个推荐最好都能回答：

  • 为什么推荐它？
  • 来源是什么？
  • 来源可信度如何？
  • 有没有动态信息冲突？
  • 哪些信息只是待核验线索？

这也是这个项目跟普通旅行规划 Demo 最大的区别。

2. 项目整体技术栈

TrustTrip 当前是一个前后端分离项目，后端负责 workflow、证据检索和验证，前端负责提交需求和展示行程结果。

层级 技术选型 作用
Backend FastAPI 提供 Trip Plan API
Workflow LangGraph 编排 Planner、POI、Verification、Review、Summary 节点
Frontend React + Vite + TailwindCSS 输入旅行需求，展示行程、证据和验证状态
RAG JSONL seed data + loader + splitter + retriever 从可信 seed data 中检索证据
Vector Store FakeVectorStore / ChromaDB 默认离线测试用 fake，真实向量库路径用 ChromaDB
Embedding FakeEmbeddingProvider / OpenAI-compatible provider 默认 fake，可选接 OpenAI-style embeddings endpoint
Evidence Provider mock / rag_fake / rag_chroma / composite_mock 不同证据来源模式
Testing pytest 覆盖配置、RAG、Chroma、embedding、动态证据、社交 skeleton、API 等

项目有一个很重要的工程原则：

1

默认路径必须离线可跑，不依赖 API key、Docker、ChromaDB、真实搜索服务或外网。

这让开发和测试更稳定。真实服务路径被设计成可选能力，通过配置显式打开，而不是默认把系统绑在外部依赖上。

每个 Agent 的职责比较清楚：

  • planner_node：生成计划大纲；
  • poi_agent_node：根据目的地和兴趣找候选 POI；
  • verification_agent_node：通过 Evidence Provider 找证据，并生成验证后的推荐；
  • review_agent_node：检查推荐质量和风险；
  • summary_agent_node：生成最终行程。

这里有一个边界要特别说明：Phase 6 的 social_trace_node 和 SocialGraphTraceOrchestrator 目前没有插入主 graph。它们只是默认关闭的 graph-adjacent skeleton，用于后续安全接入社交核验 trace。

也就是说，当前用户正常调用 API 时，不会自动跑社交 trace，也不会把社交线索写入最终行程。

4. Phase 1：Vertical Slice / 最小可用闭环

Phase 1 的目标很简单：先把产品闭环跑通。

这一阶段完成了：

  • FastAPI 后端骨架；
  • LangGraph workflow 骨架；
  • Mock Provider；
  • Trip Plan API；
  • React 前端 Planner / Result 页面；
  • 本地可运行的端到端闭环；
  • 结果页展示行程、证据、可信状态。

当时没有一上来接真实地图、搜索、天气或 LLM 服务。原因很直接：真实外部服务会让系统复杂度迅速上升，调试时很容易分不清是业务逻辑错了，还是第三方服务不稳定。

所以 Phase 1 先用了 deterministic mock provider。

1
2
3
4
5

用户请求
-> mock planner / mock POI / mock evidence
-> LangGraph workflow
-> API response
-> 前端展示

这个策略的好处是先固定数据契约。只要 mock 路径跑通，后面替换 RAG、ChromaDB、动态证据、社交信号时，就可以沿着同一个 Provider 接口逐步演进。

简单说，Phase 1 解决的是：

这个产品的最小闭环到底长什么样？

5. Phase 2：RAG Evidence Pipeline

Phase 2 开始引入 RAG evidence。

这里的 RAG 不是为了让模型“参考资料然后自由发挥”，而是为了让 Verification Agent 能基于可追踪来源进行核验。

当前 RAG 管线大致是：

1
2
3
4
5
6
7
8

JSONL seed data
-> loader
-> splitter
-> embedding provider
-> vector store
-> retriever
-> RagSearchProvider
-> Verification Agent

5.1 seed data

项目在 data/rag_sources/japan/tokyo/ 下维护 JSONL seed data，例如：

  • official POI；
  • transport guide；
  • airport guide；
  • museum info。

每条记录都带有来源信息，例如 source_name、source_url、last_verified_at。这点很重要，因为旅行规划里的证据必须能追溯。

5.2 loader 和 splitter

loader 负责读取 JSONL 文件或目录。splitter 负责把长内容切成稳定 chunk。

稳定 chunk id 很重要。它让测试可重复，也让后续 index build 更可控。

5.3 embedding provider 和 vector store

Phase 2 默认使用：

1

FakeEmbeddingProvider + FakeVectorStore

这两个组件不是为了模拟真实语义检索质量，而是为了在没有 API key、没有 ChromaDB、没有 Docker 的情况下，验证 RAG 管线的工程行为。

5.4 RagRetriever 和 RagSearchProvider

RagRetriever 负责把向量检索结果转换成 domain Evidence。

RagSearchProvider 则实现现有 SearchProvider 接口，使 Verification Agent 不需要知道证据到底来自 mock、fake RAG 还是 ChromaDB。

这就是 Provider 边界的价值：

1
2

Verification Agent 只依赖 SearchProvider
具体证据来源可以通过 ProviderFactory 切换

Evidence 不是普通字符串。它包含：

  • source type；
  • source name；
  • source URL；
  • snippet；
  • trust level；
  • retrieved time。

这让结果页可以展示“这条建议为什么可信”，而不只是输出一段模型生成的解释。

6. Phase 3：ChromaDB Integration Path

Phase 3 把向量存储从内存 fake path 扩展到 ChromaDB。

新增的核心能力包括：

  • ChromaVectorStore；
  • Chroma index builder；
  • manual indexing CLI；
  • rag_chroma runtime mode；
  • Chroma integration tests 默认 skip；
  • existing collection path；
  • index-on-startup path。

Chroma 路径大致是：

1
2
3
4
5
6
7

JSONL seed data
-> loader
-> splitter
-> embedding provider
-> ChromaVectorStore
-> RagRetriever
-> RagSearchProvider

这里保留 fake vector store 和 ChromaDB 两套路径，是一个很实际的取舍：

  • 默认开发和 CI 用 fake，速度快、无外部依赖；
  • 需要真实向量库行为时，用 ChromaDB；
  • Docker / ChromaDB 不可用时，不影响默认测试。

Phase 3 也提供了 manual indexing CLI：

1
2

cd backend
.\.venv\Scripts\python.exe -m app.rag.cli build-chroma-index --reset

不过 Phase 3 基线仍然使用 FakeEmbeddingProvider。它验证的是 ChromaDB 作为 vector store 的工程接入，不代表真实语义检索质量。

7. Phase 4：OpenAI-compatible Embedding Provider

Phase 4 解决了一个核心问题：如果一直用 fake embedding，RAG 检索结果无法代表真实语义相似度。

所以这一阶段新增了 OpenAI-compatible embedding provider。它不绑定某一家厂商，只假设对方支持 OpenAI-style /embeddings 接口：

1
2
3
4
5
6

POST {base_url}/embeddings

{
  "model": "...",
  "input": ["text 1", "text 2"]
}

7.1 fake embedding 和 real embedding 的区别

FakeEmbeddingProvider 的目标是 deterministic test，不是语义质量。

OpenAICompatibleEmbeddingProvider 的目标是接入真实 embedding 服务，让 ChromaDB 里的向量空间更接近真实语义检索。

当前配置支持：

1
2

TRUSTTRIP_EMBEDDING_PROVIDER=fake
TRUSTTRIP_EMBEDDING_PROVIDER=openai_compatible

默认仍是 fake，所以不需要 API key，也不会访问外网。

7.2 batch embedding、retry 和 timeout

provider 支持 batch embedding。请求失败时采用简单 retry：

  • 429、5xx、timeout 可以 retry；
  • 401、403、404 不 retry；
  • 超过 max_retries 后抛清晰错误；
  • 不引入 OpenAI SDK；
  • 不引入 LangChain；
  • 不引入 tenacity。

这种设计很克制。它满足基础可靠性，同时避免把一个 embedding provider 写成复杂框架。

7.3 dimension 推断

真实 embedding 模型的维度不固定。可能是 768、1024、1536、3072。

所以 Phase 4 没有强制真实 embedding 默认 64 维：

  • fake 模式默认 64；
  • openai-compatible 可以显式配置 dimension；
  • 如果 dimension 为空，provider 从首次返回向量推断；
  • 如果显式配置 dimension，则每次返回都要校验长度一致。

7.4 embedding signature

Phase 4 一个关键设计是 embedding signature。

示例：

1
2

provider=fake|model=fake-hash|dimension=64|base_host=local
provider=openai_compatible|model=text-embedding-xxx|dimension=1024|base_host=api.example.com

它用于防止这种错误：

1
2

index 阶段用模型 A
query 阶段用模型 B

或者：

1
2

index 阶段用真实 embedding
query 阶段用 fake embedding

这会导致向量空间不一致，检索结果没有意义。

signature 包含：

  • provider；
  • model；
  • dimension；
  • base host。

它不包含 API key，也不包含完整 base URL。原因很简单：API key 不能泄露，完整 URL 路径里也可能带 token 或敏感路由。只保留 hostname 已经足够判断向量空间来源。

7.5 Phase 4 hardening

Phase 4 后续做了一轮可靠性加固：

  • Settings 改成惰性加载，避免 import 阶段直接读取 env；
  • Chroma index metadata 增加 building -> ready 状态；
  • RagRetriever 把 embedding 请求失败、Chroma 临时不可用转换成可恢复错误；
  • metadata mapping bug、schema bug、TypeError、ValueError 不 fallback；
  • Chroma query 的异常边界收窄，查询失败可恢复，数据契约错误不可恢复；
  • embedding response 拒绝空向量、NaN、Infinity；
  • data[].index 混合缺失、重复、越界都会报错；
  • API key 不出现在 repr 或错误信息中。

这背后的原则是：

1
2

外部基础设施失败可以降级。
内部数据契约错误不能被静默掩盖。

8. Phase 5：Trust-first Dynamic Evidence

Phase 5 是项目里很重要的一层。

静态 RAG 能解决稳定知识，但旅行信息有大量动态变化：

  • 景点临时关闭；
  • 票务售罄；
  • 活动改期；
  • 天气预警；
  • 交通中断；
  • 快闪店、展览、演唱会等时效活动。

如果系统只依赖 seed data，很容易过时。

但动态搜索也有风险。互联网上结果很多，但可信结果不一定多。广告页、affiliate 页面、SEO 内容农场、搬运攻略、无来源博客、社交平台碎片，都可能把系统带偏。

所以 Phase 5 的核心原则是：

1

TrustTrip 不追求“搜到更多网页”，而是追求“找到更可信、可验证、可解释的证据”。

8.1 SearchPolicy

SearchPolicy 负责生成搜索意图。它不是随便拼关键词，而是根据 POI 类型和场景生成更偏官方来源的 query。

比如：

这样做的目的是减少低质量搜索结果进入系统。

SourceTrustClassifier 对来源做 deterministic 分类。

当前 source class 包括：

高可信来源通常包括：

  • 官方网站；
  • 政府网站；
  • 官方旅游局；
  • 博物馆 / 公园 / 景区 / 交通机构官网；
  • 场馆官网；
  • 官方票务平台。

低可信或排除来源包括：

  • 广告页；
  • affiliate-heavy 页面；
  • content farm；
  • resale ticket；
  • 无明确来源的博客；
  • 标题党攻略；
  • 社交平台传言。

这里还有一个安全细节：source_domain 不能信任外部传入值，必须从 source_url 解析或校验。否则恶意结果可以写：

1
2

source_url=https://evil.example/page
source_domain=gotokyo.org

如果系统直接信 source_domain，就可能把低质量来源误判成官方旅游局来源。Phase 5 hardening 已经修复了这个问题。

8.3 DynamicEvidenceCandidate

动态证据候选结构大致包含：

  • source_title；
  • source_url；
  • source_domain；
  • source_name；
  • snippet；
  • published_at；
  • updated_at；
  • retrieved_at；
  • evidence_category；
  • should_exclude；
  • excluded_reason。

它是候选，不等于最终 Evidence。

这点跟后面的社交信号类似：候选只是“可能有用的信息”，必须经过分类、过滤、合并后才可能进入最终 evidence list。

8.4 EvidenceMerger

EvidenceMerger 负责合并静态 RAG evidence 和动态 web evidence。

它做几件事：

  • 保留 static evidence；
  • 加入可信 dynamic evidence；
  • 排除广告、affiliate、content farm；
  • URL 去重；
  • 官方 / 政府 / 旅游局 / 机构来源优先；
  • 记录 excluded_sources；
  • 记录 conflict_notes；
  • 计算内部 confidence_adjustment。

confidence_adjustment 不是“网页越多越可信”。低可信来源不会提高 confidence，冲突和高风险天气还可能降低 confidence。

当前 excluded_sources、conflict_notes 和 confidence_adjustment 保存在内部结果中，没有暴露到 API 和前端。这是为了保持 API schema 兼容。

8.5 CompositeEvidenceProvider

Phase 5 新增了离线动态证据模式：

1

TRUSTTRIP_EVIDENCE_PROVIDER=composite_mock

它的组合是：

1
2
3
4
5

MockSearchProvider
+ MockWebSearchProvider
+ SourceTrustClassifier
+ EvidenceMerger
= CompositeEvidenceProvider

这个模式不访问外网，不需要 API key，也不接 MCP。它用 deterministic mock web results 模拟动态证据路径，让系统可以测试：

  • 官方来源能进入 final evidence；
  • 广告、affiliate、content farm 会被排除；
  • WebSearchRequestError 时 fallback 到 static evidence；
  • schema / mapping bug 不被吞掉。

这是一个很典型的工程策略：先把抽象、边界和测试做好，再接真实外部服务。

9. Phase 6：Region-aware Social Discovery & Verification Skeleton

Phase 6 是最新阶段，目标是让动态发现更接近真实旅行场景。

旅行信息有很强的地区性。日本旅行不能只搜英文 SEO 博客；中国大陆、韩国、欧美的官方来源、地图、票务、天气、交通平台都不一样。当地语言 query 往往更容易找到真实来源。

同时，社交平台确实能提供一些早期线索，比如排队、临时关闭、活动售罄、踩雷提醒。但社交信号不能直接当事实。

9.2 SocialSignalProvider

Phase 6 引入 SocialSignalProvider 抽象和 MockSocialSignalProvider。

它的作用不是证明事实，而是发现线索。

社交信号可以帮助发现：

  • 某个热门地点是否排队严重；
  • 某个联名咖啡厅是否需要预约；
  • 某个活动是否售罄；
  • 某条路线是否有交通延误传闻；
  • 某个打卡点是否人流过大；
  • 某个地点是否有踩雷评论。

核心模型包括：

  • SocialSearchResult；
  • EngagementSignal；
  • SocialComment。

隐私边界也很明确：

1

不保存 username、avatar、profile_url、user_id 等个人隐私字段。

9.3 EngagementSignalRanker

EngagementSignalRanker 根据浏览量、点赞、收藏、评论、分享等数据计算 discovery ranking score。

9.5 SocialDiscoveryService

SocialDiscoveryService 把社交搜索结果转换成 SocialDiscoveryCandidate。

它做几件事：

  • 输入 SocialSearchResult 列表；
  • 使用 RegionalSearchPolicy 得到结构化地区上下文；
  • 用 EngagementSignalRanker 计算 discovery score；
  • 用 CommentSignalExtractor 提取 fragment signals；
  • 输出仍然 needs_verification=True 的候选；
  • 不生成 Evidence。

这里有一个 Phase 6 hardening 里修复的地区过滤问题。

旧逻辑类似：

1

return any(term.lower() in haystack for term in location_terms)

这会导致目标是 Tokyo / Japan 时，Osaka venue in Japan 因为命中 Japan 被错误保留。

新逻辑改成“最具体地区优先匹配”：

1
2
3
4

否则有 region -> 必须匹配 region
否则有 country -> 必须匹配 country
Unknown / 无结构化地区 -> 保守保留

所以：

1
2
3

目标：city=Tokyo, country=Japan
候选：Tokyo anime cafe in Japan -> 保留
候选：Osaka venue in Japan -> 排除

这更符合 Region-aware Discovery 的语义。

RequestVerificationTrace 是 request-scoped 内部 trace。

10. 为什么一直强调“不自动转 Evidence”

这个项目里反复强调一件事：

1

社交信号只能提出待核验事项，不能直接生成可信事实。

原因很简单。社交媒体的信息有价值，但它不是权威来源。

一个评论说“这家店搬了”，它可能是真的，也可能是用户记错了，也可能是旧信息。一个帖子说“票卖完了”，可能只是某个平台的库存卖完，不代表官方售罄。

所以系统必须把它们放进待核验流程：

1
2
3
4
5

SocialComment
-> FragmentSignal
-> PendingVerificationItem
-> VerificationQuery
-> trusted-source verification

即使 VerificationOutcomeStatus.CONFIRMED，当前也不能自动转 Evidence。

未来要做 Evidence conversion，必须先定义：

  • claim_type -> acceptable trusted source class 矩阵；
  • trusted source content matching；
  • Evidence conversion rules；
  • EvidenceMerger integration。

这看起来保守，但它能防止一个很危险的问题：

系统看起来“确认了”，但其实只是把 UGC 包装成了可信证据。

TrustTrip 的核心不是“更会生成”，而是“不该信的时候不信”。

11. 错误处理与 fallback 设计

TrustTrip 的错误处理分成两类。

第一类是可恢复的基础设施错误：

  • embedding request timeout；
  • ChromaDB 临时不可用；
  • WebSearchRequestError；
  • 外部 provider timeout；
  • rate limit。

这些可以 fallback。

比如 RagRetriever 把 EmbeddingRequestError、ChromaVectorStoreError 转成 RagRetrievalError，再由 RagSearchProvider fallback 到 mock evidence。

第二类是不可恢复的数据契约或编程错误：

  • embedding 配置错误；
  • signature mismatch；
  • metadata 映射错误；
  • TypeError / ValueError；
  • schema bug；
  • Chroma 返回结果格式不符合预期；
  • source domain 与 URL 不一致。

这些不能 fallback。

否则系统会把内部 bug 伪装成“外部服务失败”，然后悄悄返回 mock 结果，开发者根本发现不了问题。

这个原则贯穿 Phase 4 到 Phase 6：

1
2

外部服务失败可以降级。
内部数据契约错误必须暴露。

在社交 runtime skeleton 里也一样：

  • not_found 是业务 outcome；
  • infrastructure_error 是基础设施 outcome；
  • 两者不能混在一起。

总结

TrustTrip 现在还不是一个接完所有真实外部服务的产品，但它已经完成了可信旅行规划系统里最重要的工程骨架。

它从一开始就没有把“生成行程”当成唯一目标，而是围绕“推荐是否可信”来设计系统：

  • RAG 提供静态可信证据；
  • ChromaDB 和真实 embedding 提供更接近真实检索的路径；
  • Dynamic Evidence 处理实时网页来源；
  • SourceTrustClassifier 排除低质量信息；
  • Social Discovery 只产生待核验线索；
  • RequestVerificationTrace 保持内部可追踪；
  • 主 graph 和 API 仍保持稳定兼容。

如果后续继续做，最自然的路线是：

  1. 接真实 Web Search Provider；
  2. 接真实 WeatherProvider；
  3. 定义 Evidence conversion rules；
  4. 把 verified social outcomes 安全接入 graph；
  5. 设计 debug endpoint 或可选 trace 展示；
  6. 最后再考虑 MCP、地图、酒店、机票等真实旅行服务。

这个项目最值得讲的地方，不是用了多少技术名词，而是它始终坚持一个边界：

1

生成可以很快，信任必须有证据。
